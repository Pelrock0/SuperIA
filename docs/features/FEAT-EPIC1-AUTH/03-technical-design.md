# Technical Design: FEAT-EPIC1-AUTH

## Overview

This design implements JWT-based authentication for Superia using `tymon/jwt-auth` on Laravel 12 with a React SPA frontend. The system consumes invitation tokens generated by FEAT-EPIC0-LANDING (HU-004), implements full auth lifecycle (register, login, password reset, profile, account deletion), and enforces RGPD compliance through a soft-delete/hard-delete pipeline.

The architecture follows hexagonal principles: thin controllers delegate to services, business logic lives in the service layer, and infrastructure concerns (email, JWT, database) are isolated. The React frontend manages JWT tokens via httpOnly cookies (set by Laravel) and uses an Axios interceptor for automatic token refresh.

## Architecture

### Component Boundaries

| Layer | Responsibilities | Key Classes/Modules |
|-------|-----------------|---------------------|
| Domain | User entity, password rules, account states, deletion policy | `App\Models\User`, `App\Models\LoginAttempt`, `App\Models\AccountDeletionLog` |
| Services | Auth orchestration, registration flow, lockout logic, deletion pipeline, token management | `AuthService`, `RegistrationService`, `AccountDeletionService` |
| Infrastructure | JWT tokens, email dispatch, database, scheduled jobs | `tymon/jwt-auth`, Mailables, Migrations, `DeleteExpiredAccountsCommand` |
| Controllers/API | HTTP interface, request validation, response formatting | `Auth\RegisterController`, `Auth\LoginController`, `Auth\PasswordResetController`, `Auth\ProfileController`, `Auth\AccountDeletionController` |
| Frontend | React pages, auth state, token refresh, protected routes | `RegisterPage`, `LoginPage`, `ProfilePage`, `AuthProvider`, `ProtectedRoute`, `api.js` (Axios instance) |

### Data Flow

#### Registration Flow (HU-101)
```
1. User clicks invitation link → GET /register?token=xxx
2. React loads RegisterPage → calls GET /api/auth/invitation/{token}
3. Backend: RegistrationService.validateInvitation(token)
   → WaitlistService.findByInvitationToken(token)
   → Returns { valid: true, email: "...", name: "..." } or 404
4. User fills form → POST /api/auth/register { token, name, password, password_confirmation, privacy_accepted }
5. Backend: RegistrationService.register()
   → DB::transaction {
       a. Validate invitation token (re-check)
       b. Create User (email_verified_at = null)
       c. Update WaitlistEntry status → 'registered'
       d. Queue VerificationMail with signed URL
     }
6. User clicks email verification link → GET /api/auth/verify-email/{id}/{hash}
7. Backend: RegistrationService.verifyEmail()
   → Set email_verified_at = now()
   → Issue JWT tokens (access + refresh)
   → Redirect to /app with tokens set as httpOnly cookies
```

#### Login Flow (HU-102)
```
1. User submits → POST /api/auth/login { email, password, remember }
2. Backend: AuthService.login()
   → Check account lockout (LoginAttempt count for email in last 15min)
   → If locked: return 429 with lockout message
   → Attempt auth via JWTAuth::attempt()
   → If fail: record LoginAttempt, return 401 generic message
   → If success: clear LoginAttempt records for user
   → Issue JWT access token (15min) + refresh token (session or 30 days if remember)
   → Set tokens as httpOnly cookies
```

#### Password Reset Flow (HU-103)
```
1. POST /api/auth/forgot-password { email }
   → Always return same success message
   → If email exists: generate token in password_reset_tokens, queue PasswordResetMail
2. POST /api/auth/reset-password { token, email, password, password_confirmation }
   → Validate token (1 hour, single-use)
   → Update password (bcrypt cost 12)
   → Delete token (single-use)
   → Invalidate all existing JWT tokens for user (increment jwt_version on User)
   → Redirect to login
```

#### Account Deletion Flow (HU-105)
```
1. POST /api/auth/delete-account { password }
2. Backend: AccountDeletionService.initiateDelete()
   → DB::transaction {
       a. Verify password
       b. Transfer shared list ownership (future-ready: no-op if no lists exist yet)
       c. Soft-delete user (deleted_at = now(), scheduled_hard_delete_at = now + 30 days)
       d. Create AccountDeletionLog (hashed_user_id, timestamp, reason: 'user_request')
       e. Invalidate all JWT tokens (increment jwt_version)
       f. Queue AccountDeletionMail
     }
3. Scheduled command (daily): DeleteExpiredAccountsCommand
   → Find users where scheduled_hard_delete_at <= now()
   → Hard-delete: user record, owned non-shared lists, items, history
```

### Transaction Boundaries

| Operation | Transaction Scope | Side Effects (post-commit) |
|-----------|-------------------|---------------------------|
| Register | Create User + Update WaitlistEntry | Queue VerificationMail |
| Login | Record/Clear LoginAttempt | Set cookies |
| Password Reset | Update password + Delete token + Increment jwt_version | Queue notification email |
| Profile Update | Update User fields | None |
| Account Deletion | Soft-delete User + Transfer ownership + Create audit log + Increment jwt_version | Queue AccountDeletionMail |
| Hard Delete (batch) | Delete User + cascade data per user | None |

Emails are always queued AFTER transaction commits to prevent sending on rollback.

## Data Model

### User Table Modifications (migration: `add_auth_fields_to_users_table`)

| Column | Type | Purpose |
|--------|------|---------|
| `jwt_version` | `unsignedInteger, default 0` | Incremented to invalidate all tokens on password change/deletion |
| `deleted_at` | `softDeletes` | Soft delete for RGPD |
| `scheduled_hard_delete_at` | `timestamp, nullable` | When to run hard delete |
| `privacy_accepted_at` | `timestamp, nullable` | RGPD consent timestamp |

### New Table: `login_attempts`

| Column | Type | Purpose |
|--------|------|---------|
| `id` | `bigIncrements` | PK |
| `email` | `string(255), index` | Target email (not FK — track attempts for non-existent emails too) |
| `ip_address` | `string(45)` | Request IP |
| `attempted_at` | `timestamp` | When attempt occurred |

Index: composite on `(email, attempted_at)` for lockout queries.

### New Table: `account_deletion_logs`

| Column | Type | Purpose |
|--------|------|---------|
| `id` | `bigIncrements` | PK |
| `hashed_user_id` | `string(64)` | SHA-256 of user ID (no PII) |
| `reason` | `enum('user_request', 'admin_action')` | Deletion reason |
| `deleted_at` | `timestamp` | When deletion was initiated |

No foreign keys — this table survives user hard-delete for audit.

### Existing Table: `password_reset_tokens`

Already exists in default Laravel migration. Configuration in `config/auth.php` already sets `expire: 60` (minutes). Will use Laravel's built-in `Password` broker — no custom table needed.

### API Endpoints

| Endpoint | Method | Auth | Purpose | Controller |

| `/api/auth/verify-email/{id}/{hash}` | GET | No (signed URL) | Verify email address | RegisterController@verifyEmail |
| `/api/auth/login` | POST | No | Login, return JWT | LoginController@login |
| `/api/auth/logout` | POST | JWT | Invalidate current token | LoginController@logout |
| `/api/auth/refresh` | POST | JWT (refresh) | Refresh access token | LoginController@refresh |

| `/api/auth/reset-password` | POST | No | Reset password with token | PasswordResetController@resetPassword |
| `/api/profile` | GET | JWT | Get current user profile | ProfileController@show |

| `/api/profile/password` | PUT | JWT | Change password | ProfileController@changePassword |

## JWT Strategy

### Token Architecture

| Token | TTL | Storage | Purpose |
|-------|-----|---------|---------|
| Access Token | 15 minutes | httpOnly cookie `superia_access` | API authentication |
| Refresh Token | 30 days (remember) / session (no remember) | httpOnly cookie `superia_refresh` | Renew access token |

### Why httpOnly Cookies (not localStorage)

| Option | Pros | Cons | Decision |
|--------|------|------|----------|
| httpOnly cookies | XSS-proof, automatic on requests | CSRF needed, SameSite helps | **Selected** |
| localStorage | Simple, no CSRF | Vulnerable to XSS, manual header management | Rejected: XSS risk |

Cookies will use `SameSite=Lax` + `Secure` (in production) + `HttpOnly`. CSRF protection via Laravel's built-in `VerifyCsrfToken` middleware for cookie-based auth, or a custom `X-XSRF-TOKEN` header approach.

### Token Invalidation

`jwt_version` column on User model. When a token is issued, the current `jwt_version` is embedded in the JWT payload. On every authenticated request, middleware checks that the token's version matches the user's current `jwt_version`. Incrementing `jwt_version` invalidates ALL existing tokens instantly.

Used on: password change, password reset, account deletion.

## Frontend Architecture

### Auth State Management

`AuthContext` provides:
- `user` — current user object or null
- `isAuthenticated` — boolean
- `login(email, password, remember)` — calls API, sets state
- `logout()` — calls API, clears state
- `refreshUser()` — re-fetches user profile

No Zustand for auth — React Context is sufficient for auth state (single concern, no complex derived state). Zustand reserved for future app state (lists, items).

### Axios Interceptor (api.js)

```
- Adds withCredentials: true (send cookies)
- Response interceptor: on 401, attempt /api/auth/refresh
  - If refresh succeeds: retry original request
  - If refresh fails: redirect to /login, clear auth state
```

### Route Structure

```jsx
<BrowserRouter>
  <AuthProvider>
    <Routes>
      {/* Public */}
      <Route path="/" element={<LandingPage />} />

      <Route path="/login" element={<LoginPage />} />
      <Route path="/forgot-password" element={<ForgotPasswordPage />} />

```


## Performance Considerations

### Query Optimization

- `login_attempts` query: `WHERE email = ? AND attempted_at > ?` — covered by composite index `(email, attempted_at)`
- Token lookup: `password_reset_tokens` has PK on email — fast
- `jwt_version` check: single column read on User model per request — negligible
- Soft-deleted users: `SoftDeletes` trait adds `WHERE deleted_at IS NULL` — default index on `deleted_at` sufficient at Superia's scale

### No Caching Needed

At current scale (waitlist-stage product), no Redis/cache layer for auth. Token validation is stateless (JWT signature check + single DB read for jwt_version). Revisit if user base exceeds 10K active.

## Trade-offs

| Option | Pros | Cons | Decision |
|--------|------|------|----------|
| `tymon/jwt-auth` | True JWT, explicit access+refresh, stateless | May need fork for Laravel 12, extra dependency | **Selected** (stakeholder decision) |
| `laravel/sanctum` | First-party, well-maintained, SPA support | Token-based not true JWT, no built-in refresh mechanism | Rejected |
| httpOnly cookies for tokens | XSS-proof | Requires CSRF protection | **Selected** (security-first) |
| localStorage for tokens | Simple | XSS vulnerable | Rejected |
| `jwt_version` for invalidation | Instant invalidation, no blacklist table | 1 DB read per request | **Selected** (simpler than token blacklist) |
| Token blacklist table | No extra column on User | Grows forever, needs cleanup job | Rejected |
| Separate `api.php` routes file | Laravel convention | Extra file, project uses `web.php` for API already | Rejected: follow existing pattern |

## Risks & Mitigations

| Risk | Impact | Probability | Mitigation |
|------|--------|-------------|------------|
| `tymon/jwt-auth` incompatible with Laravel 12 | High | Medium | Check before `composer require`. Fallback: `php-open-source-saver/jwt-auth` (actively maintained fork). |
| Mailtrap rate limits in dev | Low | Low | Queue emails with retries. Mailtrap free tier is sufficient for dev. |
| Account lockout abused as DoS | Medium | Low | Lockout is per email, not IP. Attacker needs valid email. Future: add CAPTCHA (out of scope). |
| Hard-delete batch job removes data prematurely | High | Low | Idempotent job. 30-day buffer. Audit log survives deletion. Dry-run mode for first deploys. |
| Cookie SameSite issues in dev (different ports) | Medium | Medium | Use `SameSite=Lax` in dev. Ensure frontend and backend share same domain via Vite proxy or same-origin setup. |

## Implementation Notes

1. **Install `tymon/jwt-auth` first** — verify Laravel 12 compatibility before writing any code. If incompatible, switch to `php-open-source-saver/jwt-auth` immediately.
2. **Use `php artisan make:*` commands** for controllers, requests, models, migrations, mailables, tests — as required by core.md.
3. **Registration consumes existing WaitlistService** — call `WaitlistService::findByInvitationToken()` and update status to 'registered'.
4. **Password hashing**: Laravel defaults to bcrypt. Set `BCRYPT_ROUNDS=12` in `.env.example`.
5. **Emails**: extend existing Blade email templates pattern from FEAT-EPIC0-LANDING.
6. **Frontend**: pull Stitch designs via MCP for RegisterPage, LoginPage, ProfilePage.
7. **Tests**: 100% coverage. Feature tests for all endpoints (happy + failure + edge + security). Unit tests for services and middleware.
