Wireframes - Guardado parcial de recomendaciones semanales

Feature ID: FEAT-REC-SAVE-PARTIAL | Created: 2026-05-04

🔄 User Flow

1

Abrir resumen

Usuario navega a /weekly-summary. Ve N recomendaciones, todas marcadas por defecto.

→
2

Ajustar selección

Marca/desmarca items. Contador del botón se actualiza en vivo.

→
3

Pulsar Guardar

Abre bottom sheet "Guardar en…" con listas activas + opción nueva.

→
4

Elegir destino

Selecciona lista existente o "+ Nueva lista" (si <3 activas).

→
5

Confirmar

Items se guardan, se eliminan del payload, redirección a la lista destino.

📱 Mobile-first
Todas las pantallas se diseñan para mobile (375px) primero. En desktop el bottom sheet se renderiza como modal centrado (max-width 480px). El resto de la página mantiene el layout actual de WeeklySummaryPage (max-width 672px). Design tokens del proyecto: primary #003e54, accent #6FFBBE, error #ffdad6, fondo #f7f9fb, fuente Inter.

Todos los items vienen marcados al abrir la página. Mantiene la affordance visual actual (defaultChecked) y minimiza fricción para el caso más común: el usuario quiere todas las recomendaciones. 🔁 Alternativas Consideradas

Opción Pros Cons Decisión
Bottom sheet mobile / modal desktop (mismo componente) Patrón nativo iOS/Android, gesto familiar (swipe down), encaja con design language actual de la página, escala bien con varias listas ~1h extra de animación + a11y (focus trap) Seleccionada
Modal único centrado en mobile y desktop Menos código, menos a testear Menos pulido en mobile, no aprovecha gestos nativos, rompe el patrón habitual de la app Rechazada
Dropdown inline bajo el botón "Guardar" Sin modal, más rápido para 1-2 listas Rompe el flow vertical de la página, no acomoda el botón "+ Nueva lista" + scroll si crece, mala UX en mobile Rechazada
Step separado: primero seleccionar items en pantalla A, luego ir a pantalla B con destino Cada paso simple Doble navegación, más fricción, rompe la sensación de flow rápido del resumen Rechazada
Default: ningún item marcado al abrir Decisión consciente del usuario para cada item Fricción alta para el caso común (querer todos), añade tap-tap-tap antes de poder guardar nada Rechazada
Items duplicados: crear duplicado / omitir / preguntar Más explícito Inconsistente con el comportamiento ya existente al añadir items en una lista (ya suma cantidades). Romper la consistencia confunde al usuario. Rechazada — se reusa la lógica existente (suma de cantidades)

⚠️ Error Handling & Feedback

Éxito (banner top)
✓ 2 items añadidos a "Cena del finde". Quedan 3 pendientes.
Error de red
No se pudieron guardar los items. Inténtalo de nuevo.
Error 422 (validación)
Selección inválida. Recarga la página y vuelve a intentarlo.
Error 403 (FREEMIUM_LIMIT)
Has alcanzado el límite de 3 listas activas. Archiva una lista o elige una existente.
📱 Responsive Behavior
Mobile (≤768px): bottom sheet pegado al borde inferior, ocupa hasta 90% de altura si la lista crece, drag handle visible, swipe down para cerrar.
Desktop (>768px): mismo componente como modal centrado, max-width 480px, fondo overlay rgba(0,0,0,0.5), click fuera para cerrar, ESC también cierra.
A11y: focus trap dentro del sheet/modal mientras está abierto, foco inicial en el primer item de lista, aria-modal="true", role="dialog", aria-labelledby al título "Guardar en…". Cada checkbox del resumen con aria-checked y label descriptivo. Contador del CTA con aria-live="polite".

🚨 UX Risks

Risks identificados
1. Confusión por mutación del resumen: el usuario puede esperar que el resumen completo siga ahí tras guardar (modelo mental "ya lo guardé pero sigue visible"). Mitigación: banner de éxito explícito que dice cuántos items se movieron y cuántos quedan pendientes.
2. Pérdida de selección al cambiar de pestaña: si el usuario desmarca varios y por error sale de la página, pierde el estado. Mitigación: la selección es ephemeral (no se persiste); el resumen vuelve a abrir con todos marcados. Aceptable porque el coste de re-marcar es bajo.
3. Suma de cantidades poco visible: al añadir "Leche 2L" a una lista que ya tiene "Leche 1L", el resultado es 3L pero el usuario no lo ve hasta entrar a la lista. Mitigación: redirección automática a la lista destino tras 1.5s (igual que hoy con convertToList).
4. Sheet con scroll incómodo si premium tiene >5 listas: fuera del alcance actual (límite freemium ≤3 listas activas). Si se eliminara en el futuro, aplicar max-height del sheet con scroll interno, lista virtualizada si crece mucho.
5. Doble tap en CTA confirmar genera doble guardado: mitigación: botón disabled con estado loading durante la request (ya patrón existente en la página actual).
