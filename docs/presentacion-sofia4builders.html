01 · CONTEXTO

El problema: la IA generativa sin guardarraíles

Le pides a un LLM que "implemente una feature" y te devuelve código. ¿Pero está bien diseñado, probado, seguro y alineado con el negocio? Sin un proceso, no.

SIN SISTEMA

Lo que pasa por defecto

  • Salta el análisis de scope — empieza a codear
  • Tests "si quedan ganas"
  • Mezcla dominio, framework y BD
  • Vocabulario inconsistente entre features
  • Vulnerabilidades no detectadas
  • 30-40 % de re-trabajo por requisitos mal capturados
CON SOFIA4BUILDERS

Workflow forzado

  • Cada feature pasa por 6 pasos auditables
  • Cada paso = un agente especializado
  • Cobertura 100 % es gate, no recomendación
  • Glosario DDD por bounded context
  • Auditoría OWASP automática antes de mergear
  • State machine bloquea atajos
02 · CONCEPTOS

¿Qué es un "agente IA" aquí?

Un agente = un LLM cualquiera (Claude, GPT, Gemini, Llama, Mistral…) + rol + instrucciones + herramientas (leer archivos, ejecutar comandos, escribir código). El sistema no impone modelo: cada agente declara cuál usa en su frontmatter.

ROL

Quién es

"Eres un Product Owner. Tu trabajo es escribir un PRD que sea un contrato entre negocio e ingeniería."

SKILL

Cómo lo hace

Checklist + plantillas + criterios de aceptación. Define el formato exacto del output y refuta excusas comunes.

HERRAMIENTAS

Qué puede tocar

Leer/escribir archivos, ejecutar tests, lanzar sub-agentes, navegar (en frontend), correr CLI del proyecto.

Clave: un agente solo hace UNA cosa. No "implementa y revisa". El que revisa es otro agente, sin contexto sesgado del que escribió. Cada gate es independiente.

06 · ORQUESTACIÓN

El CLI: la state machine que no deja saltarse pasos

cli/cli.py — el state machine escrito en Python. Mantiene un JSON por feature en cli/state/ y bloquea cualquier avance sin artefactos válidos.

Comandos clave

# crea feature → estado inicial S1
python cli/cli.py create FEAT-001

# genera el prompt de contexto
# (reglas + agente + skill + outputs previos)
python cli/cli.py prepare FEAT-001 --mode=claude

# valida artefactos y avanza al siguiente paso
python cli/cli.py approve FEAT-001

# si falla un review, vuelve a S4 (max 3 iter)
python cli/cli.py review-failed FEAT-001 "reason"

Qué valida approve

  • El artefacto del paso existe (01-scope.md, 02-prd.md…)
  • Glosario DDD presente antes de S3
  • Tests existen y se ejecutan de verdad (php artisan test, npm test, pytest…)
  • Detección de cambios UI vía git diff → activa S5-UX
  • Checksum SHA-256 del state (integridad)
  • Contador de iteraciones de review — bloqueo a las 3
07 · GUARDARRAÍLES

Reglas no negociables

.cursor/core/core.md — reglas que aplican a TODOS los agentes. Sin excepciones.

ARQUITECTURA

Hexagonal + DDD

  • Dominio sin imports de framework ni ORM
  • Use cases ↔ DTOs (nunca request/response)
  • Repository = port en dominio, adapter en infra
  • Agregado: una raíz, invariantes adentro
TESTING

100 % cobertura, sin trampas

  • Cobertura 100 % — bloqueante
  • BD real, no SQLite. Transacciones que rollback
  • Cubre happy + failure + edge + security
  • Test-gate ejecuta los tests, no se fía
ARTEFACTOS

Si no está escrito, no existe

  • Sin scope aprobado → no hay PRD
  • Sin PRD aprobado → no hay diseño
  • Sin diseño aprobado → no hay código
  • TBD pendiente = STOP
VOCABULARIO

Ubiquitous Language

  • Glosario por bounded context
  • El PRD debe referenciar el glosario
  • Mismo término → misma definición
  • Evita el clásico "anular vs cancelar"
07.2 · MEMORIA EN CAPAS

Documentación y funcionalidad como memoria por capas

Los LLMs olvidan entre conversaciones. El sistema lo resuelve con una memoria estratificada: cada capa tiene un alcance, un ciclo de vida y un consumidor distintos. Cuando el agente arranca, la memoria se ensambla de abajo arriba.

┌──────────────────────────────────────────────────────────────────┐ │ L5 · MEMORIA DE CONVERSACIÓN ← efímera · solo este turno │ ├──────────────────────────────────────────────────────────────────┤ │ L4 · ESTADO DE FEATURE ← cli/state/FEAT-XXX.json │ ├──────────────────────────────────────────────────────────────────┤ │ L3 · ARTEFACTOS DE FEATURE ← docs/features/FEAT-XXX/ │ ├──────────────────────────────────────────────────────────────────┤ │ L2 · GLOSARIOS Y CONTEXTOS DDD ← docs/contexts/{ctx}/ │ ├──────────────────────────────────────────────────────────────────┤ │ L1 · SKILLS + AGENTES ← .cursor/skills + .cursor/agents ├──────────────────────────────────────────────────────────────────┤ │ L0 · CORE.MD · REGLAS DE ORO ← .cursor/core/core.md │ └──────────────────────────────────────────────────────────────────┘ ↓ ENSAMBLADO POR `prepare` ↓ PROMPT DEL AGENTE
L0

Core · las reglas de oro

Qué es: .cursor/core/core.md. Reglas no negociables válidas para TODOS los agentes (hexagonal, DDD, testing 100 %, TBD = STOP).

Ciclo: raramente cambia · cambio = decisión arquitectónica.

Quién la lee: los 10 agentes, en cada paso.

L1

Skills + agentes · el "cómo"

Qué es: .cursor/skills/ (recetas por paso) + .cursor/agents/ (rol y modelo). Define cómo escribir un PRD, hacer un code review, etc.

Ciclo: evoluciona con la metodología.

Quién la lee: el agente del paso actual, sólo el suyo.

L2

Glosarios DDD · vocabulario del negocio

Qué es: docs/contexts/{ctx}/00-glossary.md. Ubiquitous Language por bounded context. Memoria semántica del dominio.

Ciclo: crece feature a feature; se actualiza cuando aparecen términos nuevos.

Quién la lee: product-owner, architect, backend, code-reviewer.

L3

Artefactos de feature · trazabilidad

Qué es: docs/features/FEAT-XXX/01-scope.md · 02-prd.md · 03-design.md · 05-reviews/*. La historia decisional de cada feature.

Ciclo: append-only · versionado en git.

Quién la lee: el agente del paso siguiente — lee los outputs de los pasos anteriores.

L4

Estado de feature · puntero de ejecución

Qué es: cli/state/FEAT-XXX.json. Status (S1…S6), iteraciones de review, tiempo, checksum, métricas.

Ciclo: se muta en cada approve / review-failed.

Quién la lee: el CLI (gate de aprobación) y el dashboard.

L5

Conversación · memoria efímera

Qué es: el contexto que el LLM mantiene durante una sola sesión. Se descarta al cerrar.

Ciclo: minutos · muere con la ventana.

Quién la lee: sólo el agente actual mientras dura el turno.

Cómo se ensambla la memoria al arrancar un paso

# `python cli/cli.py prepare FEAT-001 --mode=claude`
# compone el prompt del agente leyendo de abajo arriba:

[L0] .cursor/core/core.md                       # reglas de oro
[L1] .cursor/agents/<rol-del-paso>.md            # quién es
[L1] .cursor/skills/<skill-del-paso>.md          # cómo lo hace
[L2] docs/contexts/<ctx>/00-glossary.md          # vocabulario
[L3] docs/features/FEAT-001/01-scope.md          # outputs previos
[L3] docs/features/FEAT-001/02-prd.md            # …
[L4] cli/state/FEAT-001.json                     # dónde estoy
   ↓
prompt completo · contexto saturado de forma intencional
Por qué funciona: ningún agente "se acuerda" — todos leen. La memoria vive en archivos versionados, no en la cabeza del LLM. Por eso el sistema es reproducible: dos devs distintos en dos máquinas distintas obtienen el mismo contexto y el mismo output. Y por eso es portable: cualquier framework agéntico que sepa leer markdown puede ejecutar el mismo workflow.
EFÍMERA

L5 · Conversación

Vive en RAM. Se pierde al cerrar el chat.

VOLÁTIL

L4 · Estado

Cambia a cada paso. JSON mutado por el CLI.

PERSISTENTE

L0–L3 · Markdown + git

Versionada, auditable, trazable. La verdadera memoria del sistema.

07.5 · ARQUITECTURA

DDD como columna vertebral

Domain-Driven Design no es opcional aquí — está incrustado en el workflow. El sistema bloquea cualquier feature que no respete los principios estratégicos y tácticos.

DDD ESTRATÉGICO

Mapear el negocio

  • Bounded Context: cada dominio aislado en docs/contexts/{context}/
  • Ubiquitous Language: glosario 00-glossary.md obligatorio antes de S3
  • Context Maps: relaciones entre contextos documentadas
  • El PRD del paso S2 debe referenciar el glosario del contexto
DDD TÁCTICO

Modelar el dominio

  • Aggregate: una raíz, invariantes adentro, persistencia atómica
  • Repository: port en dominio, adapter en infrastructure (hexagonal)
  • Value Objects: inmutables, sin identidad propia
  • Domain Events: emitidos por agregados, consumidos por otros contextos

Cómo el sistema lo hace cumplir

GateValidación DDDSi falla
S2 → S3El PRD referencia el glosario del bounded contextBloqueo · resolver primero
S3Existe docs/contexts/{ctx}/00-glossary.mdCLI no permite avanzar
S4 (impl)Dominio sin imports de framework / ORMCode-reviewer rechaza
S4 (impl)Repositorios = ports en dominio, adapter en infraCode-reviewer rechaza
S4 (impl)Use cases hablan DTOs, no request/responseCode-reviewer rechaza
S5-CODEAgregados con invariantes, persistencia atómicaVuelve a S4
Por qué importa: sin Ubiquitous Language, "cancelar" en producto significa "anular" en BD y "borrar" en frontend. El glosario por contexto fuerza un solo término — y el agente que escribe el PRD lo referencia, el architect lo respeta, el dev lo usa en código. Trazabilidad lingüística completa.

09 · S5 · REVIEWS

Cuatro jueces independientes

En S5 se lanzan 4 reviews — cada una con un agente distinto, sin contexto compartido. Si uno falla, vuelve a S4.

S5-CODE

Code Review

Patrones, hexagonal, naming, complejidad, code smells.

S5-SEC

Security Review

OWASP Top 10 2021 + LLM Top 10 v2 · npm audit · gitleaks · SAST · CVE scan · SSRF · auth bypass.

S5-TEST

Test Gate

Ejecuta los tests de verdad. Valida cobertura 100 %. Si baja del umbral, bloquea.

S5-UX

UX Review

Compara la UI implementada con los wireframes aprobados. Accesibilidad WCAG 2.1 AA.

Política de bloqueo: 3 iteraciones fallidas → feature BLOQUEADA. Requiere --force o escalación humana.

12 · POR QUÉ IMPORTA

¿Qué lo hace distinto?

No es "un LLM haciendo código". Es un proceso de ingeniería ejecutado por agentes — con la calidad y la trazabilidad que pedirías a un equipo humano senior.

01

State machine forzada

El CLI bloquea atajos. Si el PRD no está, no hay diseño. Si los tests no pasan, no hay merge.

02

Coverage 100 % como gate

Test-gate ejecuta los tests reales contra una BD real. No se fía de lo que dice el agente que codifica.

03

Artifact-driven

Toda decisión queda escrita en markdown versionable. PRD = contrato. Diseño = contrato. Sin ambigüedad.

04

DDD integrado

Glosarios por bounded context. Mismo término en producto, código y BD. Sin "anular vs cancelar".

05

Multi-stack real

Mismo flujo en Laravel, Node, Django, FastAPI, Go o Rust. Las reglas específicas se inyectan al prompt.

06

Seguridad auditada

OWASP 2021 + LLM Top 10 v2 + scans automáticos antes de cada merge. Encuentra CVEs en deps.

07

Portable · framework-agnóstico

Las definiciones viven en archivos markdown + YAML, no en SDK propietario. Funciona hoy con Cursor y Claude Code de forma nativa, y se adapta fácilmente a cualquier framework agéntico (LangGraph, AutoGen, CrewAI, agentes custom). Cambias el "transport"; las reglas, skills y gates no se tocan.

EN UNA FRASE

Sofia4Builders convierte un LLM en un equipo de ingeniería con disciplina.

El LLM ya sabe escribir código. Lo que falta es el proceso: scope, diseño, tests, revisión, seguridad, trazabilidad. Eso es lo que el sistema impone — no como recomendación, sino como gate técnico.
